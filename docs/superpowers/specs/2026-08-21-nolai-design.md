# 놀AI 설계 문서

- **작성일**: 2026-08-21
- **서비스명**: 놀AI (nolai)
- **도메인**: `nolai.kr` (메인), `nolai.ai` (브랜드 방어)
- **상태**: 설계 확정, 구현 계획 수립 전

---

## 1. 서비스 정의

만 10~13세(초등 3~6학년) 한국 어린이가 AI의 작동 원리를 **글로 읽지 않고 손으로 만져서** 이해하는 온라인 놀이터.

기존 어린이 코딩 교육(스크래치, 엔트리, code.org)은 프로그래밍 기초를 다룬다. 놀AI는 그 시장에 들어가지 않는다. 대신 **"AI가 어떻게 생각하는가"**를 다룬다 — 임베딩, 벡터검색, RAG 같은 개념을 아이 눈높이에서 시각화하고 직접 조작하게 한다. 이 영역은 어른용 자료조차 대부분 글과 도표뿐이며, 어린이용은 사실상 비어 있다.

### 타겟

**만 10~13세, 단일 페르소나.**

"초등학생 전체"로 넓히지 않는다. 저학년(7~9세)과 고학년(10~13세)은 읽기 능력, 입력 방식(타이핑 가능 여부), 추상 개념 수용도, 사용 상황(보호자 동반 여부)이 모두 달라 사실상 다른 사용자다. 둘을 모두 만족시키려면 콘텐츠를 두 벌 만들어야 한다.

10~13세로 정한 이유는 두 가지다. **혼자 들어와서 놀 수 있는 최저 나이**이면서, 임베딩·벡터검색을 은유로 얼버무리지 않고 진짜로 이해시킬 수 있는 최저 나이다.

저학년용 쉬운 모드는 만들지 않는다. 나중에 필요해지면 그때 붙인다.

---

## 2. 핵심 설계 원칙

모든 레슨과 화면이 지켜야 할 네 가지.

1. **설명보다 조작이 먼저 온다.** 부엉이의 말은 지시가 아니라 아이 행동에 대한 반응이어야 한다.
2. **틀린 답이 없다.** 아이가 무엇을 하든 놀이터는 반응하고, 왜 그렇게 되는지만 보여준다. 실패 상태를 만들지 않는다.
3. **한 레슨은 10분.** 이 나이대 집중력의 현실적 상한.
4. **모든 숫자는 진짜다.** 임베딩 좌표는 실제 모델로 미리 계산한 값이다. 아이가 나중에 커서 확인해도 거짓말이 아니어야 한다.

## 3. 사용자 여정

### 첫 방문 — 60초 안에 놀이터까지

```
랜딩 ─→ 이름 정하기 ─→ 비밀코드 발급 ─→ 첫 레슨 놀이터
        (랜덤 추천      (크게 표시,      (설명 없이
         3개 중 선택)    "적어둬!")       바로 조작)
```

가입 화면의 입력란은 **닉네임 하나**다. 기본 동작은 랜덤 추천 3개 중 클릭해서 고르는 것이고, 직접 입력은 옵션이다. 이 방식이 실명 입력을 구조적으로 막으면서 동시에 가입 마찰을 없앤다.

랜딩 페이지는 부모·교사가 검색으로 도착하는 입구이기도 하다. **SEO 대상은 랜딩 페이지뿐**이다.

### 재방문

```
같은 기기  ─→ (자동 입장) ─→ 내 방
다른 기기  ─→ 닉네임+코드 ─→ 내 방
                               ├─ 진도 지도   (어디까지 왔나)
                               ├─ 배지 선반   (모은 것)
                               └─ 내 작품     (놀이터에서 만든 결과물)
```

"내 방"은 재방문의 유일한 이유다. 놀이터만 있으면 데모이지 서비스가 아니다. 따라서 첫 버전에 반드시 포함한다.

**같은 기기에서는 비밀코드를 다시 입력하지 않는다.** 서명된 세션 쿠키(만료 1년)를 발급하므로, 코드는 기기를 바꿀 때만 필요하다. 매 방문마다 코드를 요구하면 이탈한다.

## 4. 계정 — 닉네임 + 비밀코드

### 왜 정식 회원가입을 하지 않는가

타겟 연령이 10~13세이므로 **전원이 만 14세 미만**이다. 한국 개인정보보호법상 만 14세 미만의 개인정보를 수집하려면 법정대리인 동의 절차가 필수다. 이메일 회원가입 하나를 넣는 순간 부모 동의 확인 플로우, 동의 기록 보관, 아동용 개인정보처리방침이 모두 따라온다.

더 현실적인 문제는 이탈이다. 아이는 부모를 부르러 가다가 그냥 나간다.

닉네임과 비밀코드는 개인정보가 아니므로 동의 절차 대상이 아니다. 그러면서 아이 입장에서는 **"내 계정"이 맞다** — 진도, 배지, 작품이 서버에 쌓이고 기기를 바꿔도 유지된다. 비밀코드를 받는 경험 자체가 게임 같아서 오히려 선호된다.

정식 회원가입(부모 동의 포함)은 사용자가 늘면 그때 도입한다.

### 사양

**닉네임**
- 기본: 랜덤 단어 조합 3개를 제시하고 클릭해서 선택 (`번개토끼`, `무지개상어`, `초코로봇`)
- 직접 입력은 옵션. 실명 패턴과 금칙어를 필터링한다
- **중복 허용**. 로그인은 닉네임과 코드의 조합으로 이루어지므로 닉네임 자체는 유일할 필요가 없다

**비밀코드**
- 6자리, 문자셋은 `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31자)
- 혼동 문자 `0 O 1 I L`을 제외한다. 아이가 종이에 적었다가 못 알아보면 계정을 잃는다
- 저장은 해시(bcrypt). 닉네임으로 후보를 조회한 뒤 코드를 검증한다

**로그인**
- 닉네임과 비밀코드가 **둘 다** 일치해야 한다. 코드만으로 로그인하면 아무 코드나 찍어서 남의 방에 들어갈 수 있다
- IP당 분당 5회 시도 제한

**코드 분실**
- 개인정보를 받지 않으므로 **복구 수단이 없다.** 이것은 설계상 감수하는 비용이다
- 완화책: 발급 화면에서 코드를 크게 표시하고 "이미지로 저장" 버튼을 제공한다. 발급 시점에 분실하면 복구할 수 없음을 명확히 경고한다
- 실무적으로는 세션 쿠키가 1년간 유지되므로, 같은 기기를 쓰는 한 코드를 쓸 일이 없다

## 5. 레슨 구조

### 뼈대 — 만져보기가 먼저, 이름은 나중에

모든 레슨은 다음 5단계를 따른다.

| 단계 | 하는 일 |
|---|---|
| **hook** | 부엉이가 질문을 던진다. 답은 주지 않는다 |
| **play** | 설명 없이 놀이터를 조작한다. 부엉이는 반응만 한다 |
| **name** | "방금 한 게 임베딩이야"라고 이름을 붙인다 |
| **challenge** | 배운 것으로 문제를 푼다 |
| **reward** | 배지를 받고 작품이 내 방에 저장된다 |

추상 개념은 설명을 먼저 들으면 튕겨 나간다. 손으로 먼저 겪은 뒤에 설명이 붙는다.

### 저장 형태 — 겁데기는 데이터, 놀이터는 코드

레슨의 **놀이터 부분은 개념마다 인터랙션이 완전히 다르다.** 임베딩은 지도 위에서 점을 끌어다 놓는 것이고, 벡터검색은 거리를 재는 것이다. 이를 "설정으로 조립 가능한 범용 위젯"으로 일반화하려는 시도는 어느 개념에도 맞지 않는 결과를 낳는다.

반대로 놀이터를 뺀 나머지(부엉이 대사, 개념 설명, 도전 문제, 배지)는 개념이 달라도 형태가 같다.

따라서 **레슨 1개 = JSON 파일 1개 + 놀이터 컴포넌트 이름 하나**로 저장한다.

```json
{
  "id": "embedding-map",
  "order": 1,
  "title": "비슷한 말끼리 모여라",
  "playground": "EmbeddingMap",
  "dataset": "words-animals-vehicles",

  "steps": [
    { "type": "hook",
      "owl": "컴퓨터는 '강아지'라는 말을 몰라. 그럼 어떻게 알아듣지?" },

    { "type": "play",
      "owl": ["아무거나 끌어다 놔봐!",
              "어? 강아지랑 고양이가 붙었네. 왜 그럴까?",
              "자동차도 한번 놔볼래?"],
      "goal": { "minPlaced": 5 } },

    { "type": "name",
      "concept": "임베딩",
      "body": "컴퓨터는 말을 숫자로 바꿔서 기억해. 비슷한 뜻일수록 숫자가 비슷해지고, 그래서 지도에서 가까이 붙는 거야." },

    { "type": "challenge",
      "question": "'호랑이'는 어디에 놓일까?",
      "choices": ["강아지 근처", "자동차 근처", "사과 근처"],
      "answer": 0,
      "explain": "호랑이도 동물이니까 강아지·고양이 쪽으로 가!" },

    { "type": "reward", "badge": "map-explorer" }
  ]
}
```

문구 수정, 난이도 조정, 도전 문제 추가는 이 파일만 고치면 된다. 코드를 열지 않는다.

레슨 JSON은 zod 스키마로 검증하며, CI에서 전체 레슨 파일을 검사한다.

### 놀이터 컴포넌트 계약

**놀이터는 레슨 흐름을 모른다.** 이것이 핵심 설계 결정이다.

```ts
interface PlaygroundProps {
  data: PlaygroundDataset                   // 미리 계산된 진짜 임베딩 좌표
  onEvent: (e: PlaygroundEvent) => void     // "아이가 방금 이걸 했어요"
  onArtifact: (a: Artifact) => void         // "이걸 만들었어요" → 내 방에 저장
}
```

`EmbeddingMap`은 점을 그리고 끄는 것만 안다. 부엉이가 언제 무슨 말을 하는지, 다음 단계가 무엇인지는 바깥의 `LessonRunner`가 `onEvent`를 받아 판단한다.

이렇게 분리해야 (1) 새 개념을 추가할 때 놀이터 하나만 쓰면 되고, (2) 놀이터를 단독으로 열어 테스트할 수 있다. 놀이터 안에 부엉이 대사를 박아 넣으면 레슨마다 놀이터를 복사하게 된다.

## 6. 실습 방식 — 미리 계산된 진짜 데이터

실행 중 LLM이나 임베딩 API를 **호출하지 않는다.**

임베딩은 사전에 실제 모델로 계산해 정적 데이터로 저장한다. 아이는 진짜 AI가 만든 숫자를 만지지만, 서비스는 API를 한 번도 부르지 않는다.

이 선택으로 세 가지가 동시에 해결된다.

- **비용 0** — 사용자가 늘어도 추론 비용이 없다
- **유해 콘텐츠 위험 0** — 아동 대상 서비스에서 LLM 자유 입력은 필터링과 어뷰징 방지 설계를 반드시 요구한다. 아예 없앤다
- **속도** — 네트워크 왕복 없이 즉시 반응한다

**이로 인한 제약을 명시한다.** 아이가 임의의 문장을 자유 입력할 수 없다. 질문과 단어는 **미리 준비된 카드 중에서 고른다.** 카드를 충분히 많이(20개 이상) 두어 자유도를 체감하게 한다.

## 7. 첫 버전 범위

### 뼈대 (콘텐츠와 무관)

- **온보딩** — 닉네임 고르기 → 비밀코드 발급
- **내 방** — 진도 지도 · 배지 선반 · 내 작품
- **레슨 러너** — JSON을 읽어 5단계를 진행
- **DB** — kids / progress / artifacts / badges
- **랜딩 페이지** — SEO 대상

### 레슨 2개

**레슨 1 — 비슷한 말끼리 모여라 (임베딩)**

- 놀이터: `EmbeddingMap`
- 데이터: 단어 20개 내외 (동물 / 탈것 / 음식 3개 카테고리) + 실제 임베딩을 2D로 투영한 좌표
- 조작: 단어 카드를 지도 아무 곳에나 끌어다 놓으면, 자석에 끌리듯 **진짜 자리로 스프링 애니메이션하며 이동**한다. 가까운 단어끼리는 사이에 선이 생기고, 가까울수록 굵어진다
- 아하: *내가 아무 데나 놔도 컴퓨터가 아는 자리로 간다. 비슷한 것끼리 모인다.*
- 이 방식은 "틀린 답이 없다" 원칙을 지킨다. 아이는 실패하지 않고, 컴퓨터가 이미 답을 알고 있다는 것만 보게 된다
- 배지: `map-explorer` (표시명 "지도 탐험가")

**레슨 2 — 가장 가까운 걸 찾아줘 (벡터검색)**

- 놀이터: `NearestSearch`
- 데이터: 짧은 문장 조각 30개 내외(동물 백과사전 형식) + 질문 카드 20장 + 미리 계산된 유사도
- 조작: 질문 카드를 고르면 지도에 질문이 한 점으로 나타나고, 가까운 문장 3개로 빛이 뻗어나가며 순위가 매겨진다
- 아하: *검색은 "똑같은 단어"를 찾는 게 아니라 "뜻이 가까운 것"을 찾는 거구나.*
- 배지: `path-finder` (표시명 "길 찾기 대장")

배지는 `badges` 테이블에 영문 id로 저장하고, 표시명과 아이콘은 프론트엔드 배지 정의 파일에서 관리한다.

두 레슨은 이어져서 하나의 이야기를 만든다 — 말을 지도 위 위치로 바꾸고(1), 그 지도에서 가장 가까운 것을 찾는다(2). 레슨 2 끝에서 아이가 직접 검색을 성공시키는 순간이 첫 버전의 절정이다.

### 첫 버전에 넣지 않는 것

- 실제 LLM API 호출
- 토큰 · RAG · 환각 레슨 (2차)
- 부모 · 교사 대시보드
- 결제 및 유료화
- 저학년(7~9세) 모드
- 모바일 앱, 다국어

## 8. 데이터 모델

```
kids
  id            uuid pk
  nickname      text              (인덱스, 중복 허용)
  code_hash     text
  created_at    timestamptz

progress
  kid_id        uuid fk
  lesson_id     text
  status        text              (not_started | in_progress | done)
  completed_at  timestamptz
  pk (kid_id, lesson_id)

artifacts
  id            uuid pk
  kid_id        uuid fk
  lesson_id     text
  payload       jsonb             (놀이터가 만든 결과물)
  created_at    timestamptz

badges
  kid_id        uuid fk
  badge_id      text
  earned_at     timestamptz
  pk (kid_id, badge_id)
```

Supabase RLS를 적용해 각 아이는 자신의 행만 읽고 쓸 수 있게 한다. 세션 쿠키의 `kid_id`를 기준으로 삼는다.

## 9. 아트 디렉션

### 톤 — 팝 캔디, 전체 밝은 톤

두꺼운 검은 외곽선(`#1F2430`), 고채도 색, 아래로 떨어지는 입체 그림자. 요즘 게임 UI의 정석이며 조작 유도가 가장 강하다. 아이가 설명 없이 먼저 만져야 하는 구조에서 "이거 눌러도 돼"라는 신호가 명확해야 한다.

파스텔 톤은 채택하지 않는다. 10~13세는 유아용으로 보이는 것에 민감하다.

### 화려함을 어디에 쓰는가

화려함을 화면 전체에 균일하게 뿌리지 않는다. 놀이터 안에서 아이가 읽어야 하는 정보는 점들 사이의 **거리**인데, 배경이 번쩍이면 그것이 보이지 않는다.

| 구역 | 연출 |
|---|---|
| 홈 · 내 방 · 배지 획득 · 레슨 시작/완료 | 최대한 화려하게 — 파티클, 효과음, 캐릭터 애니메이션 |
| 놀이터 안쪽 | 배경은 절제, 대신 **반응**을 화려하게 |

놀이터에서 화려함은 배경 장식이 아니라 *"내가 점을 놓으면 스프링처럼 튕기며 자리를 찾아가는 것"*으로 쓴다. 더 재미있고 개념도 더 잘 보인다.

### 색 규칙

밝은 배경에서는 거리가 색에 묻힐 수 있다. 다음 규칙으로 해결한다.

- **거리는 색이 아니라 선으로 표현한다.** 두 단어가 가까우면 사이에 선이 생기고, 가까울수록 굵어진다
- **색은 카테고리에만 쓰고 3색으로 제한한다** (동물 / 탈것 / 음식)
- 놀이터 지도 영역은 UI 배경과 다른 밝기 + 두꺼운 외곽선으로 명확히 구분한다

### 효과음

첫 버전에 포함한다. 아이 대상 서비스에서 효과음 유무는 체감 완성도를 크게 가른다. 단, 음소거 버튼을 눈에 띄는 곳에 둔다(교실·도서관 사용 대비).

## 10. 기술 스택

**Next.js (App Router) + Supabase + Vercel**

- 서버 로직은 Route Handler로 충분하다. 별도 API 서버를 두면 관리 대상만 늘고 얻는 것이 없다
- Vercel 무료 + Supabase 무료 티어로 유지비가 사실상 0
- 랜딩 페이지 SEO가 필요하므로 SSR이 되는 편이 낫다

### 폴더 구조

```
nolai/
├── frontend/              # Next.js — 사실상 전부
│   ├── app/               # 라우트
│   ├── lessons/           # 레슨 JSON
│   ├── playgrounds/       # 놀이터 컴포넌트
│   └── datasets/          # 미리 계산된 임베딩 좌표
├── database/              # Supabase 마이그레이션
├── tools/embed/           # 파이썬(uv) — 임베딩 사전 계산
├── docs/
└── CLAUDE.md
```

`backend/`가 없는 것은 의도적이다. CLAUDE.md의 표준 풀스택 구조에서 벗어나지만, Supabase와 Route Handler가 서버 역할을 모두 수행하므로 빈 껍데기 서버를 두지 않는다.

`tools/embed/`만 파이썬이며 uv로 관리한다. 배포와 무관하게 로컬에서 가끔 실행하는 도구다.

### 임베딩 사전 계산 파이프라인

`tools/embed/`가 하는 일:

1. 단어·문장 목록(YAML)을 읽는다
2. 임베딩 모델로 벡터를 계산한다
3. 2D로 투영한다
4. `frontend/datasets/*.json`으로 출력한다

출력물은 git에 커밋한다. 빌드 시점에 재계산하지 않는다 — 좌표가 바뀌면 레슨의 도전 문제 정답이 흔들리기 때문이다.

## 11. 에러 처리

| 상황 | 처리 |
|---|---|
| 비밀코드 분실 | 복구 불가. 발급 시점에 명확히 경고하고 이미지 저장 버튼 제공. 세션 쿠키 1년으로 실질 발생률을 낮춤 |
| 네트워크 실패 | 진도·작품을 localStorage에 먼저 쓰고 백그라운드로 동기화. 아이는 끊김 없이 계속 논다 |
| 동기화 충돌 | 서버 우선이 아니라 **완료 상태 우선**. 진도는 되돌아가지 않는다 |
| 잘못된 레슨 JSON | zod 검증 실패 시 CI에서 빌드를 막는다. 런타임에 깨진 레슨을 노출하지 않는다 |
| 로그인 무차별 시도 | IP당 분당 5회 제한. 초과 시 대기 안내 |

## 12. 테스트 전략

- **놀이터 컴포넌트** — 단위 테스트. 좌표 계산, 이벤트 발생, 아티팩트 출력
- **레슨 러너** — JSON 스텝 진행, 조건 충족 시 다음 단계 전환
- **인증** — 코드 생성 시 금지 문자 미포함, 닉네임+코드 조합 검증, rate limit 동작
- **레슨 데이터** — 전체 레슨 JSON의 zod 스키마 검증 (CI)
- **E2E (Playwright)** — 온보딩 → 레슨 1 완료 → 배지 획득 → 내 방에 작품 표시까지 한 흐름
